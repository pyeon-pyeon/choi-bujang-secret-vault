# 1~11단계 요청 실측표 작성 절차

이 문서는 실행 절차입니다. 문서 추가나 로컬 시험 통과는 실제 배포 API 시험 실행을 뜻하지 않습니다. 공개 제공 목록의 **41종 attackId·단계·기대 결과**를 operations/defense-catalog.json에 보관했습니다. operations/defense-tests.json의 각 행은 아직 **미실행**입니다. 제공 목록에는 각 실제 시험의 메서드·정확한 경로·실행 증거가 없으므로 이를 임의로 채우지 않습니다. 임의의 시험을 만들어 공식 목록으로 대체하거나 41종을 통과로 채우지 않습니다.

## 하나의 표로 관리

보관된 제공 목록의 attackId와 기대 결과를 유지하여 한 항목당 한 행을 만듭니다. 공개 41종 목록에는 12단계 복합 시험 3종도 포함되어 있습니다. 같은 시험의 재실행은 행을 추가하여 이전 실패도 보존합니다. 정상 요청과 금지 요청을 별도 행으로 기록합니다. 실제 결과를 입력하기 전에는 아래처럼 미실행으로 둡니다.

| 시험 번호 / 단계 | 유형 | 대상 버전 / 요청 | 기대 결과 | 실제 API 결과 | 서버 요청 ID | 확인 시각(UTC) | 근거 출처 / 판정 |
|---|---|---|---|---|---|---|---|
| anonymous_note_read / 1 | 금지 | 실행 경로·대상 버전 미확인 | 보호 본문 없이 거부 | 미실행 | — | — | 제공 목록 / 미실행 |

위는 제공 목록의 첫 행을 보여주는 형식 예시입니다. 전체 41행은 operations/defense-tests.json과 서버의 coverage.records에서 같은 ID로 대조합니다. 정의만 확보했으므로 현재는 41행 모두 미실행이며 완료 건수로 집계하지 않습니다. 단계별 준비 순서는 README의 복구 후 1~9단계 재검증 표, 10단계 복원 안내, 11단계 기기 승인 안내를 참고합니다. 그 안내 역시 공식 41종 정의를 대신하지 않습니다.

## 실제 요청과 기록

1. 배포의 `/aleph.json`에서 커밋을 확인하고 표에 대상 커밋·배포 주소를 기록합니다. 로그인 계정은 A/B, 기기는 시험용 가명으로만 구분합니다. 서버 승인된 A 기기를 준비하되 미등록 시험은 별도 세션으로 유지합니다. DB 자료·다른 서비스·감사 이력을 보존하고 생성·수정·삭제·복원은 지정한 공개 가능한 시험 자료에만 수행합니다.
2. 브라우저 개발자 도구 **Network → Preserve log**를 켭니다. 정상 요청은 승인된 A 기기에서 기존 화면으로 실행합니다. 금지 요청은 공식 시험이 정한 비로그인·B·미승인 등의 조건에서 실행합니다. 각 요청의 실제 메서드와 경로를 확인합니다. 계정·기기 조건을 바꾸었으면 이전 화면 자료를 새 응답으로 오인하지 않습니다.
3. Network에서 해당 요청의 HTTP 상태와 응답의 허용/거부 결과를 확인합니다. 표에는 `HTTP 200 / 본인 한 건 확인`, `HTTP 404 / 자료 없음`처럼 결과만 적습니다. 메모 본문·비밀번호·토큰·쿠키·공개 키를 포함한 전체 요청/응답은 복사하지 않습니다. 거부 사유 코드는 비밀값 없는 고정 코드만 기록합니다. 수정·삭제 성공은 후속 GET이나 승인된 서버 확인으로 실제 반영 여부까지 확인하고 그 요청도 연결해 기록합니다.
4. 응답에 서버가 발급한 요청 식별 헤더/필드가 있으면 그 값을 기록합니다. 예: `X-Request-ID`. **없으면 `미제공`**으로 적습니다. 임의 UUID, 브라우저 Network 내부 번호, 기기 승인 응답의 `requestId`를 HTTP 요청 ID로 대신하지 않습니다. 승인 `requestId`는 등록 신청 번호입니다. 서버 로그와 연결할 수 없으면 `요청 ID 대조 미확인`으로 남깁니다.
5. 응답을 확인한 실제 시각을 UTC ISO 8601로 기록합니다. 브라우저 콘솔의 `new Date().toISOString()`으로 확인 시각을 얻을 수 있습니다. 이것은 응답 확인 시각이며 서버 처리 시각이나 회수 경과 시간의 증거로 사용하지 않습니다.
6. 서버가 제공하는 가린 기록이 있으면 요청 ID·메서드·경로·상태·시각을 대조합니다. 본문·신원 원문·인증 헤더는 표에 넣지 않습니다. 가린 기록이 없으면 `서버 기록 대조 미확인`으로 표시합니다. 인증 정보가 포함될 수 있는 HAR 파일이나 Copy as cURL 결과를 제출하지 않습니다.

## 판정과 집계

- 정상 요청은 실제 허용 응답 **및 기대한 동작**이 확인되어야 합니다. 단순 2xx, 로그인 HTML로의 리다이렉트, 빈 응답은 정상 자료 읽기 성공의 증거가 아닙니다.
- 금지 요청은 기대한 거부 결과 **및 자료 미반환·변경 없음**을 확인합니다. 5xx나 연결 실패는 접근 통제 통과로 세지 않습니다. API별 401/403/404 등 기대 상태는 공식 시험과 실제 계약에 맞춰 기록합니다.
- `실측 통과`, `실측 실패`, `실측 일부·판정 보류`, `미실행`을 구분합니다. 요청 ID나 서버 기록 대조가 없는 경우 그 공백을 표시하고 전체 증거가 완성됐다고 쓰지 않습니다. 모의 시험은 `로컬/모의` 출처로만 적고 실제 API 결과 칸을 채우지 않습니다.
- 6~9단계 엔진 판정·탐지·실제 회수는 제공 엔진/심판의 실측이 있어야 합니다. 현재 API 상태만으로 엔진 판정이나 회수 성공을 추정하지 않습니다. 10단계는 사본 검증·복원 후 비교, 11단계는 승인 전 거부와 승인 후 정상 요청을 각각 기록합니다.
- 집계에는 공식 시험 번호의 중복을 제거하고 최신 실행 결과를 사용하되 이전 행은 보존합니다. 목록이 정확히 41종인지 먼저 확인합니다. 공식 목록을 확보하지 못했거나 미실행이 남으면 `41종 완료`로 표시하지 않습니다. 정상 허용과 금지 거부 각각의 실측 건수를 따로 보고합니다.

표는 `artifacts/request-tests.md`에 저장하면 Git에 포함되지 않습니다. 표에 기입할 실측이 없는 현재 상태는 **정상 허용 미실행 / 금지 거부 미실행 / 공개 41종 정의 확보·실행 증거 미확보**입니다. 다음 실행에서 관찰된 결과만 갱신합니다.
