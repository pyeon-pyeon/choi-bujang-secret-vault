1. 기존 작업 폴더를 덮어쓰지 말고 별도 폴더에 복제한 뒤 검사 커밋을 선택합니다. Node.js 22 이상과 Git이 필요합니다. 아래 명령은 셸 종류와 관계없이 한 줄씩 실행합니다.

```bash

cd vault-reproduce
git checkout --detach afa012ce45c935182d22154246077293ac94e99c
git log -1 --oneline
npm ci
```

2. 다음 순서로 로컬 가상 시험과 빌드를 실행합니다. 명령이 실패하면 첫 오류를 기록하고 뒤 단계를 성공으로 표시하지 않습니다. XDR 명령은 해당 result.json을 갱신하므로 별도 재현 폴더에서 실행합니다.

```bash
npm run decider:test

```

위 명령은 요청별 시험이며 상시 서버를 띄우지 않습니다. 로컬 빌드만으로 Vercel 서버 함수나 ALEPH SDP 엔진이 실행되지는 않습니다. 이 문서 작성 시 다시 실행한 범위는 앞서 명시한 기준 커밋의 세 가상 시험뿐입니다. 나머지는 재현할 절차입니다.

3. 실제 자료실은 Vercel에서 이 저장소를 Import하고 vercel.json의 `npm run build`·public 출력 설정을 사용합니다. 검사할 커밋이 실제 배포됐는지 `/aleph.json`의 commit으로 확인합니다. Vercel **프로젝트 Settings → Environment Variables**에 SUPABASE_URL과 서버 전용 SUPABASE_SECRET_KEY를 직접 설정합니다. 인증 설정에 필요한 공개 키도 서버 설정에서 관리합니다. 값 자체를 README·Git·제출 묶음에 넣지 않습니다. 기존 학습 DB를 재사용할 때 SQL을 무조건 다시 실행하지 말고 적용 상태와 권한부터 확인합니다. 새 학습 DB는 supabase의 2~5단계 자료/권한 SQL, 10단계 복원 SQL, 11단계 승인 SQL을 단계별 설명과 함께 검토해 적용합니다. 4단계 authenticated 권한을 마지막 상태로 남기지 않고 5단계 직접 권한 회수를 적용합니다. 시험 계정·메모·안전 사본은 별도 준비 사항이며 자동 생성됐다고 가정하지 않습니다.
4. 배포 화면에서 A 로그인 → 기기 승인 요청 → 관리자가 Supabase의 vault_devices에서 신청과 소유자를 확인해 승인 → 화면의 상태 확인 → 본인 자료 요청 순서로 확인합니다. 승인 버튼만으로 승인되지 않습니다. 이어 비로그인·미승인·B의 타인 자료 요청 거부를 확인합니다. [요청 실측표](docs/REQUEST_TEST_MATRIX.md)에 실제 결과를 기록합니다. 엔진 가상 사건의 통과와 실제 API의 통과는 따로 기록합니다.

### 중지

로컬 시험은 완료되면 종료되며 진행 중인 명령은 Ctrl+C로 중단합니다. 브라우저 앱은 로그아웃하고 창을 닫습니다. 로그아웃은 Vercel 배포 중지가 아니며 설치 앱 삭제도 기기 승인 회수가 아닙니다. 특정 기기를 중지하려면 관리자가 해당 vault_devices 행을 revoked로 바꾸고 후속 보호 요청의 거부를 확인합니다. 서비스 전체 중지가 필요하면 Vercel 운영자가 제공하는 배포 접근 제한/중지 절차를 사용하고 외부 비로그인 요청으로 실제 차단을 확인합니다. 이 저장소에는 전체 서비스를 중지하는 명령이 없습니다. ALEPH SDP 엔진의 중지·회수는 제공 운영 절차를 따르며 학생이 엔진용 명령을 임의로 만들지 않습니다.

### 복구와 복구 후 확인

먼저 git status·diff와 배포 커밋, DB 상태를 확인하여 기존 작업과 감사 이력을 보존합니다. 코드 재배포와 DB 자료 복구는 별도 작업입니다. 실제 침해 전 검증 사본·독립 신뢰 지문이 없거나 검증에 실패하면 정책 복원을 중단합니다. [정책 비교·격리 시험 복원 절차](docs/POLICY_RESTORE.md)에 따라 읽기 전용 비교 → 버전·변경 범위 확인 → 확인 지문 검토 → 격리 시험 폴더 복원 순서로 실행하며 실제 운영 정책은 이 도구로 변경하지 않습니다.

메모는 관리자 검증을 거친 비공개 사본이 있을 때만 승인된 시험 계정 B로 **POST /api/restore/:noteId**를 실행합니다. ID·소유자·내용 해시를 대조하고 다른 메모·감사 이력은 보존합니다. 엔진의 현재 허용 경로에 복원 경로가 포함됐다고 가정하지 않습니다. 복구 후 아래 1~9단계 재검증 순서에 10단계 복원 결과와 11단계 승인 전 거부·승인 후 허용을 더해 실측표에 기록합니다. 아직 실행하지 않은 41종과 실제 회수·복원은 미실행으로 남깁니다. 비밀값·원본 토큰·메모 본문·비공개 사본을 재현 묶음에 포장하지 않습니다.

## 12단계 저장점: 탈환 작전실과 재현 안내

[요청 실측표 작성 절차](docs/REQUEST_TEST_MATRIX.md)에 정상·금지 요청, 기대 결과, 실제 API 결과, 서버 요청 ID, 확인 시각을 한 표로 기록하는 방법을 추가했습니다. 공식 41종 목록은 현재 저장소에 없고 이번 실제 API 시험은 미실행입니다. 로컬/모의 결과를 실측 통과로 옮기지 않습니다. 서버 요청 ID가 없으면 미제공으로 기록하고 기기 승인 신청 번호와 구분합니다. 정상 허용과 금지 거부 모두 실제 응답과 동작을 확인한 뒤 결과를 기록합니다. 기존 11단계 저장점 기록과 다른 작업은 보존합니다.

작전실은 로그인·서버 기기 승인을 확인한 GET /api/operations의 가린 응답만 표시합니다. 규칙 수는 실제 RULE_IDS, 탐지 수는 검증된 로컬 XDR 기록에서 계산하며 운영 탐지로 표시하지 않습니다. 실제 회수와 복구 버전은 연결된 실측 기록이 없어 미확인으로 표시합니다. 승인 취소·로그아웃 시 화면 자료를 지웁니다. 단계 설정과 빌드 식별 생성은 12단계를 지원합니다. 재확인은 `node --test test/operations-summary.test.mjs test/device-flow.test.mjs test/zone-routes.test.mjs`와 `npm run build -- --local`입니다. 로컬/모의 시험과 빌드를 확인했으며 실제 배포·41종 요청 실측은 미실행입니다. 배포 주소·원격 저장소·발급자·원본 API·복원 경로는 유지하고 작전실 GET 경로를 allowedRoutes에 추가했습니다.

## 11단계 저장점: 설치형 화면과 서버 승인 흐름

manifest·아이콘·설치 안내·오프라인 화면을 추가했습니다. 서비스 워커는 offline.html만 캐시하며 메모·인증·API 응답을 저장하지 않습니다. 설치를 기기 승인으로 취급하지 않습니다.

POST /api/device는 로그인 신원을 검증해 pending 기기 요청만 만들고 GET /api/device는 해당 계정의 서버 등록 상태를 조회합니다. 브라우저 JavaScript는 기기 키·토큰을 localStorage·sessionStorage·IndexedDB에 저장하지 않습니다. 등록 세션의 무작위 식별값은 서버가 Secure·HttpOnly·SameSite=Strict 쿠키로 전달하고 DB에는 SHA-256 지문만 저장합니다. 이 승인 기록은 브라우저 등록 상태이며 하드웨어 인증이나 제공 엔진의 승인 상태를 대신하지 않습니다. 기존 엔진 deviceRegistered 판정도 유지합니다.

화면은 서버가 approved를 반환하기 전 메모를 요청하거나 표시하지 않습니다. 승인 확인 뒤 기존 메모 목록·작성 화면을 엽니다. 메모·공지·복원 API도 서버 승인을 매 요청 검사해 pending/미등록/다른 계정/만료/회수는 403, 상태 DB 오류는 503으로 거부합니다. 승인 요청 본문에서 approved·owner_id 등을 받지 않습니다. 로그인과 소유자·공지 권한 검사도 그대로 수행합니다.

이 구현은 기존 Supabase에 승인 기록을 보관하므로 supabase/step11-device-approval.sql 적용이 필요합니다. 별도 프로그램·CA·기기 서명 키는 만들지 않습니다. SQL은 승인 테이블만 생성하며 서버 역할에는 SELECT와 pending 생성용 열 INSERT만 허용하고 상태 열 쓰기는 허용하지 않습니다. 관리자가 Table Editor에서 화면의 요청 번호와 실제 계정 소유자를 확인한 뒤 해당 행의 status를 approved로 바꿉니다. 클라이언트 버튼은 승인하지 않습니다. 승인 회수는 관리자가 revoked로 바꿉니다. 상태 확인 버튼이나 다음 조회로 결과를 반영합니다. 사용자가 SQL 실행 완료를 알려 주었습니다. 실제 관리자 승인·권한 결과는 미확인입니다. 승인 전에는 정상 로그인 사용자도 자료가 거부됩니다.

재확인: `node --test test/device-flow.test.mjs`. 실제 모듈을 모의 환경에서 실행해 대기만 생성·승인 전 메모 DB 조회 0건·승인 후 200·회수/다른 계정/만료 거부, 화면 승인 전 자료 요청 0건·승인 후 기존 목록 표시를 확인했습니다. 기존 판정·구역·승인 조건을 가정한 복원 시험과 로컬 빌드도 통과했습니다. 실제 브라우저 설치·기기 승인·A/B 및 심판 요청은 미실행입니다. 단계 설정은 11입니다. 기존 배포 주소·발급자·자료/복원 경로·원본 URL을 대조해 유지하고 기기 GET·POST 경로를 기록했습니다. 배포와 실제 승인은 미실행입니다. 11단계 전체 실측 완료를 주장하지 않습니다.

## 10단계 저장점_수정본: 복원 사본 재검증

정책 비교·복원 계획이 공통 readVerifiedPolicyCopy를 사용하도록 보완했습니다. 계획과 실행마다 사본을 새로 읽고 manifest의 독립 신뢰 지문·각 파일 해시를 검증한 바로 그 바이트만 복원에 사용합니다. 검증 뒤 파일을 검증 없이 다시 읽던 경로를 제거했습니다. 실행 전에 복원 버전과 변경 목록·확인 지문을 보여주는 절차는 유지합니다.

## 10단계 저장점: 정책 비교·시험 복원과 비공개 메모 한 건 복원

빌드·배포 식별 생성기는 10단계를 지원하며 로컬 빌드를 확인했습니다. 실제 SQL·사본 등록·복원·심판 실측은 미실행입니다.

정책 비교·격리 시험 복원 절차는 docs/POLICY_RESTORE.md에 기록했습니다. 실제 침해 전 검증 사본과 독립 보관한 지문이 없으므로 현재 운영 정책을 복원하지 않았습니다. 다른 서비스 규칙·감사 기록·DB는 보존합니다.

메모 복원 서비스는 notes이며 경로는 **POST /api/restore/:noteId**입니다. 빈 본문 또는 {}만 받으며 자료 ID는 경로에서만 선택합니다. 로그인 검증 후 learning_note_backups의 같은 ID·검증된 로그인 소유자·verified 사본과 내용 SHA-256을 대조합니다. 해시는 UTF-8 바이트 길이:title과 UTF-8 바이트 길이:content를 이어 붙인 문자열의 SHA-256입니다. 본문에 소유자·내용·role을 받아 복원하지 않습니다. 사본 누락·변조·타인 소유자는 본문 없이 거부합니다.

supabase/step10-note-restore.sql은 검토 후 학습 DB에서 실행하는 서버 전용 사본 테이블·트랜잭션 함수입니다. 원본 메모와 사본을 자동 생성하지 않습니다. 관리자만 침해 전 검증한 비공개 가상 사본 한 건을 등록하며 현재 손상 데이터를 안전 사본으로 자동 지정하지 않습니다. 함수는 해당 ID 한 건만 삽입/갱신하고 기존 소유자가 다르면 중단합니다. 복원 후 ID·소유자·해시를 다시 확인하며 실패 시 DB 트랜잭션 전체가 취소됩니다. 다른 메모와 감사 이력은 삭제·변경하지 않습니다.

재확인: `node --test test/note-restore.test.mjs`. 가상 B 메모 한 건으로만 API·RPC 모의 시험을 실행했습니다. 대상 ID·소유자·내용 해시 일치와 다른 메모·가상 감사 기록 보존을 확인했습니다. 실제 SQL 실행·사본 등록·실제 B 요청·배포·심판 실측은 미실행입니다. 현재 판정기는 복원 경로를 아직 허용하지 않으며 단계 설정은 10입니다. 배포 주소·발급자·기존 경로·원본 API 주소를 대조해 유지하고 실제 POST 복원 경로를 restoreRoute와 allowedRoutes에 기록했습니다. 정책 규칙·엔진 경유 복원 허용은 이번 API 요청에 추가하지 않았습니다. 서버 키는 기존 환경변수만 사용하고 응답·로그·Git에 넣지 않습니다.

## 9단계 제공 계약 정합성 수정

최신 구현은 docs/DETECT_EVENTS.md의 원래 at·method·identity.sub 사건 계약을 사용합니다. 임의로 추가했던 필수 네트워크·deviceId 조건과 확장 시험을 제거했습니다. 같은 사용자 GET의 어느 10분 구간이 120건을 초과하면 {action: propose_revocation, reasonCode: burst_read, subject}만 반환하며 120건 이하·사용자 분산·시간창 밖은 observe입니다. 네트워크나 기기를 추정하지 않습니다. 대상 subject를 기기 ID로 간주하지 않으며, 실제 기기 회수 연결·시간 측정은 심판 검증이 필요합니다. 아래 복합 신호·기기 필수 설명은 이전 구현 기록입니다. 재확인은 npm run detect:test이며 실제 회수 API나 권한 변경은 없습니다.

## 9단계 저장점: 복합 가상 탐지와 단일 기기 회수 제안

빌드·배포 식별 생성기는 9단계를 지원하며 로컬 빌드를 확인했습니다. 실제 탐지 사건 전달·회수 계약의 운영 정합성 제한은 그대로 남습니다.

src/detection-input.mjs가 시각·요청 종류·가명 사용자와 출처가 명시된 가상 네트워크·기기 ID만 추출합니다. 추가 본문·토큰·실명은 버리고 원문을 저장하거나 출력하지 않습니다. 제공 원래 계약에는 네트워크·기기가 없어 로컬 시험에 signals와 deviceId를 확장했습니다. 이 확장이 운영 심판의 실제 계약과 일치하는지는 미확인입니다.

src/detect.mjs는 같은 가명 사용자와 기기의 10분 구간에서 GET이 120건을 넘고 그 구간에 judge_fixture 출처 unusual 네트워크 사건이 함께 있을 때만 propose_revocation·burst_read·subject·deviceId를 반환합니다. 120건 이하·평소 네트워크·출처 불명·신호/기기 누락·서로 다른 사용자/기기·시간창 밖 사건은 observe입니다. 지역은 판단에 쓰지 않습니다. 한 번에 한 기기만 제안하며 실제 회수 API·권한 변경은 수행하지 않습니다. 기존 decide(request) 응답은 유지합니다.

재확인: npm run detect:test. 로컬 가상 사건 10개를 통과했습니다. 시험 형식을 이번 복합 신호와 기기 대상으로 확장했으며 원래 제공의 건수 전용 시험 통과를 의미하지 않습니다. 실제 사건 전달·회수·경과 시간 측정은 미실행이고 심판이 확인합니다. 단계는 9이며 기존 배포 주소·발급자·API 허용 경로·원본 주소를 대조해 유지합니다. 기존 자료·다른 작업·DB는 변경하지 않았습니다.

## 8단계 저장점: 전체 목록·기능 경로 차단 보완

최신 판정 안내에 맞춰 판정기에서 GET /notes 전체 목록 허용을 제거했습니다. 단건 ID 자리의 all·list·bulk·export·import·admin·search·download 및 대소문자 변형을 거부합니다. 본인 목록 GET /api/my/notes와 정상 메모 단건 GET·PUT 경로는 유지하며 소유자 비교는 최종 메모 API가 수행합니다. 공지·강사 자료 쓰기 POST·PUT·PATCH·DELETE는 판정기에서 누구에게나 거부합니다. 이전 기기·출처 검사·복합 재확인 규칙은 유지합니다.

재확인: `node --test test/zone-routes.test.mjs`. 본인 목록·단건 허용, 전체 목록·기능 경로 거부, 공지·강사 쓰기와 서비스 표기 우회 거부 시험을 통과했습니다. `npm run decider:test`와 `npm run fixture:7`도 통과했습니다. 모두 로컬 가상 요청 결과이며 실제 배포·심판 재통과는 미확인입니다. 단계 8·기존 배포 주소·발급자·실제 API 허용 경로·원본 API 주소는 기존 구현과 대조해 유지합니다. ## 4단계 기록

### 4단계 저장점 기록

자료 API는 기존 토큰 검증을 유지하고 검증된 ID와 owner_id를 대조합니다. 목록은 본인 행, 단건 GET·PUT·DELETE는 id와 owner_id를 함께 조건으로 사용합니다. 추가는 서버 ID로 소유자를 저장하고 수정은 title/body만 허용하며 기존·새 소유자를 본인으로 제한합니다. 상대 또는 없는 행은 자료 없이 404, 잘못된 수정 필드는 400, 인증 실패는 401입니다.

allowedRoutes에는 GET /api/notes, POST /api/notes, GET /api/notes/:id, PUT /api/notes/:id, DELETE /api/notes/:id를 기록했습니다. 정상 A/B 본인 CRUD와 상대 접근·소유자 변경 거부는 모의 DB로 검증했습니다. 실제 계정 A/B 시험은 미실행입니다.

supabase/step4-notes-rls.sql은 검토 후 SQL Editor에서 직접 실행합니다. 기존 PUBLIC·anon·authenticated 테이블 권한 회수, authenticated CRUD만 부여, 본인 행 RLS 네 정책, 적용 전후 명시·실제 권한 조회를 포함합니다. 이 테이블의 기존 정책을 교체하지만 행이나 다른 테이블은 건드리지 않습니다. DB 적용과 권한 결과는 미확인입니다. 서버 Secret key는 RLS를 우회하므로 API 소유자 검사도 유지합니다.

직접 Data API는 anon 키로만 확인하고 authenticated 역할 직접 접근은 점수 근거에 넣지 않습니다. 현재 anon 키 직접 점검은 미실행입니다. 로그인 없이 자료 조회 거부와 배포 식별만 실제 자기 점검에 기록하며 A/B 소유자 차단을 검증한 것처럼 보고하지 않습니다.

다시 실행: npm run build -- --local. 배포 후 화면에서 로그인해 본인 추가·수정·삭제를 확인하고, 상대 단건 접근은 404로 거부돼야 합니다. 과거 공개 커밋·배포가 남아 있는 한 과거 노출이 해소됐다고 판단하지 않습니다.

## 3단계 기록

기존 검증 도우미로 토큰을 확인하고, 누락·실패 시 자료 없이 401을 반환합니다. 추가 시 검증된 ID를 owner_id로 저장하며 목록은 로그인 사용자의 자료 배열을 반환합니다. 기존 owner_id가 NULL인 학습 자료는 보존하지만 본인 목록에는 표시하지 않습니다.

| 메서드 | 경로 | 결과 |
|---|---|---|
| GET | /api/notes | 본인 메모 배열 |
| POST | /api/notes | {id,title,body} 입력, id 생략 시 서버 UUID 생성, {id} 반환 |
| GET | /api/notes/:id | {id,title,body}; 없음/삭제 후 404 |

allowedRoutes는 실제 경로 두 개를 기록하며 각 경로의 메서드는 위 표와 API에서 제한합니다. SQL Editor에서 supabase/step3-notes-permissions.sql을 실행하면 서버 역할의 쓰기 권한만 추가됩니다. 기존 DB 행은 삭제하지 않습니다.

**의도적으로 남은 3단계 허점:** 단건 GET·PUT·DELETE에는 소유자 검사가 없습니다. 정상 B 로그인으로 A 메모 ID를 지정하면 조회·수정·삭제할 수 있습니다. 4단계에서 보완합니다. 로그인 화면은 목록 항목별 수정·삭제와 새 메모 추가를 제공합니다.

정상 계정 로그인 후 메모를 추가·수정·삭제할 수 있어야 합니다. 비로그인·잘못된 토큰은 401, 삭제된 단건 GET은 404여야 합니다. 실제 계정 CRUD와 새 배포는 아직 검증하지 않았습니다. 단계 설정은 3이며 identityProvider와 allowedRoutes를 구현에 맞춰 기록했습니다. 실제 로그인 A 성공, B의 타인 자료 수정, SQL 쓰기 권한 적용은 미실행 또는 미확인입니다. 자기 점검은 인증 없는 조회와 잘못된 토큰 조회를 실제 배포에 보내고 결과만 기록합니다. 새 커밋이 배포되기 전에는 2단계 응답이 관찰될 수 있습니다.

다시 실행: npm run build -- --local. 실제 배포 후 로그인 → 가상 메모 추가 → 수정 → 삭제를 확인합니다. 자료 API의 비로그인 요청은 401, 삭제 후 단건 조회는 404여야 합니다.

## 2단계 기록

화면은 `/api/notes`의 Vercel 서버 함수를 통해 `public.learning_notes`의 가상 메모 네 건을 읽습니다. 루트 `data.json`과 공개 `data.json`은 빈 메모 목록이며, 빌드는 메모 본문을 복사하지 않습니다. 아래 1단계 설명은 시작 당시의 동작 기록입니다.

**남은 약점:** `/api/notes`는 아직 공개 주소입니다. 로그인·소유자 검증이 없어 비로그인 방문자도 가상 메모를 읽을 수 있습니다. DB의 RLS와 브라우저 역할 권한 회수만으로 이 서버 함수의 공개 접근이 막히지는 않습니다.

Supabase SQL Editor에서 가상 메모 네 건을 등록한 상태를 유지하세요. `supabase/step2-learning-notes.sql`은 테이블 구조와 권한만 담고 본문은 포함하지 않습니다. 새 DB에서는 이 파일만 실행해도 메모가 생기지 않습니다. 기존 DB 행은 삭제하거나 수정하지 않습니다. `owner_id uuid`는 NULL 허용이며 외래키가 없습니다.

Vercel 프로젝트 Settings → Environment Variables에서 `SUPABASE_URL`과 서버 전용 `SUPABASE_SECRET_KEY`를 직접 등록하고 Redeploy하세요. 실제 값은 Git·브라우저 파일·답변에 넣지 않습니다. 함수는 DB 오류 세부 정보를 응답하거나 로그에 남기지 않습니다. 저장점 설정과 다음 빌드의 배포 식별 단계는 2입니다. 실제 배포·DB 적용 완료나 심판 통과를 의미하지 않습니다.

로컬 정적 빌드: `npm run build -- --local`. 이 명령은 서버 함수를 실행하지 않습니다. 실제 배포 후 `/`에서 네 건이 표시되고 `/api/notes` GET은 200, POST는 405, DB 설정 누락/실패는 503이어야 합니다. `/data.json`은 빈 목록이고 DB의 anon·authenticated 직접 조회는 거부되어야 합니다.


## 2단계 심판 오류 보완 (로컬 수정, 배포 미확인)

### 1. GitHub 최신 파일 검색

기존 작업 폴더를 덮어쓰지 않도록 별도 임시 복제본에서 검색합니다. 아래는 Bash/Git Bash 명령입니다. `git grep -l`은 본문 대신 일치한 파일 이름만 출력하며, 종료 코드 1은 검색 결과 없음입니다.

note_prefix='실습용 가상'

### 2. 실제 배포 응답 검색

Vercel의 Domains 주소로 비로그인 요청을 보냅니다. 인증 없는 HTTP 요청에는 브라우저 로그인 세션이 포함되지 않습니다. 응답 본문은 임시 파일에만 저장하고 검색 결과로 파일 이름만 출력하세요.

```bash
app_url='https://choi-bujang-secret-vault-xtz6.vercel.app'
deploy_review_dir=$(mktemp -d)
for path in / /data.json /aleph.json /api/notes; do
  filename=${path#/}
  filename=${filename//\//_}
  if [ -z "$filename" ]; then filename=index.html; fi
  curl --silent --show-error --max-time 30 \
    --output "$deploy_review_dir/$filename" \
    --write-out "$path HTTP %{http_code}\n" "$app_url$path"
done
rg -l -F \
  -e "$note_prefix 과제 기록" \
  -e "$note_prefix 포트폴리오 기록" \
  -e "$note_prefix 리추얼 기록" \
  -e "$note_prefix 행정 기록" "$deploy_review_dir"
```

HTTP 200뿐 아니라 JSON을 파싱해서 확인하세요. JSON이 Unicode 이스케이프로 인코딩되면 단순 문자열 검색이 일치하지 않을 수 있습니다.

`/data.json`은 정상 JSON이며 `notes`가 빈 배열이어야 합니다. `/aleph.json`의 `repoUrl`과 `commit`을 위 최신 GitHub SHA와 대조하세요. `/api/notes`는 현재 의도적으로 공개된 약점이므로 DB 연결 완료 시 비로그인 GET에도 네 건이 반환됩니다. `/`의 초기 HTML에 본문이 없어도 브라우저가 API를 호출해 표시할 수 있습니다. 시크릿 창에서 페이지를 열고 개발자 도구 Network의 `/api/notes` 응답을 함께 확인하세요. 연결 실패, 404, 503, 리다이렉트 또는 JSON 파싱 실패는 본문 제거 성공의 증거가 아닙니다. HTML이 불러오는 추가 JS 파일이 있다면 해당 파일도 검색합니다.

### 3. 과거 노출과 현재 결과를 구분

**옛 공개 커밋 또는 옛 공개 배포가 남아 있는 한 과거 노출이 해소됐다고 쓰지 않습니다.** GitHub History에서 이전 `data.json`과 `public/data.json`을 확인하고, Vercel Deployments에서 기존 개별 배포 주소의 `/data.json`도 비로그인으로 확인하세요. 최신 도메인이 새 배포를 가리키는 것만으로 이전 배포가 사라지지는 않습니다. 이 점검은 기록·배포 삭제나 Git 이력 재작성을 수행하지 않습니다.

결과는 예를 들어 “최신 정적 JSON에는 메모 없음 / 최신 GitHub 전체 문장 검색 결과를 별도 기록 / 공개 API에서는 읽기 가능 / 과거 커밋·배포 노출은 별도 잔존”처럼 범위별로 기록하세요. 복제·캐시·다운로드된 과거 자료가 회수됐다고 단정하지 않습니다. 이 문서의 절차 추가 자체는 실제 점검 실행이나 방어 성공을 의미하지 않습니다.

## 1단계 시작 당시 안내

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.
